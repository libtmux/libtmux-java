# What an operation costs, measured

Regenerated by `./gradlew operationBenchmark`. Never edit by hand.

| environment | value |
| --- | --- |
| tmux | `3.7d` |
| JVM | `25.0.3 (Eclipse Adoptium)` |
| OS | `Linux 6.18.33.2-microsoft-standard-WSL2 (amd64)` |
| CPU | `12th Gen Intel(R) Core(TM) i7-12700H, 10 cores` |
| commit | `80b2b76a2484` |

Measured 20 rounds per scenario, each scenario run 3 times on a fresh server. A wall clock shows the middle run, and the fastest and slowest either side of it where they differ, so a row that moved is not read as a row that means something. Each `ProcessTransport` dispatch starts a tmux process, so the dispatch count is the cost and the milliseconds are one machine's rendering of it; the count is identical across the runs or the table is not written at all. Read the shape.

## Collapsing round trips

The same 20 windows, asked for three ways. This is the whole of the answer to per-command process cost, so it leads.

| strategy | wall clock | commands dispatched |
| --- | --- | --- |
| `one-at-a-time` | 436 ms (396-459) | 64 |
| `batch` | 68 ms (66-76) | 5 |
| `chain` | 52 ms (48-70) | 5 |

Every row pays the same four commands for the handle it starts from and the count it ends with, so the ratio between them understates what grouping saves: the work itself is 60 commands against one.

## Narrow reads

Five sessions, one wanted. A pane or window condition is looped over each session inside tmux, so no probe comes first.

## What the staleness guard costs

A handle fences every command it sends behind `if-shell -F`, so that a handle cannot act on a tmux that replaced the one it was taken from. Both rows take a handle first, so the difference is the guard alone.

| command | wall clock | commands dispatched |
| --- | --- | --- |
| `unguarded` | 108 ms (107-119) | 22 |
| `guarded` | 91 ms (79-94) | 22 |

The guard rides inside the one command it fences, so it costs no further process. What it adds is bytes, against the 16384 a tmux command may carry.

## Push against poll

The same command, waited on three ways, 5 times: it prints a marker 200 ms after it starts, so 1000 ms of every row is the command itself. What is left is what the wait added: noticing late, and the processes spent looking.

| wait | wall clock | added per wait | commands dispatched |
| --- | --- | --- | --- |
| `poll: awaitText` | 1114 ms (1111-1126) | 22 ms | 37 |
| `push: control %output` | 1067 ms (1063-1067) | 13 ms | 15 |
| `signal: Pane.run` | 1107 ms (1104-1113) | 21 ms | 32 |

Three different costs, not one ranking. A poll spends a tmux process every 50 ms, so its count grows with how long it waits, and it notices up to one interval late. A push pays once to attach a control client — not in the count, and most of its added time over so few waits — and after that is told as output arrives, so its count is only the commands typed. `Pane.run` pays a fixed handful per command whatever the command's length: reading the pane, the wait, reading the output back, and the three tmux calls the pane's shell makes to report the end. In return it is the only one of the three that knows the command ended, and with what status.

## What an option listing costs

A listed value is escaped for display, and how it is escaped changes between releases, so names come from the listing and values from `show-options -v`, batched.

| read | wall clock | commands dispatched |
| --- | --- | --- |
| `one option` | 62 ms (45-63) | 20 |
| `all()` | 168 ms (166-186) | 40 |
| `effective()` | 165 ms (162-167) | 40 |

That is the cost: one option is one command, and a listing is two whatever its size, until it outgrows what one command may carry.

## One command, two transports

The same read, `display-message -p "#{session_name}"`, sent 200 times after 50 untimed: once as a `ProcessTransport` dispatch, a fresh tmux process per command, and once as a request over an attached `ControlClient`, which stays connected between requests. Nanoseconds, because that is the size of the gap a persistent control-mode transport would close.

| transport | median per command | p95 per command | commands |
| --- | --- | --- | --- |
| `process: one command` | 2358.1 µs | 3157.9 µs | 200 |
| `control: one command (attached)` | 217.6 µs | 366.6 µs | 200 |

This justifies keeping the process transport the default and control opt-in; it does not justify making a persistent control transport the default, and it does not offset what control mode gives up to get there. A control reply is an acknowledgement, not a completion — a queued `run-shell` finishes later, off this measurement. Standard input has no per-command channel in control mode, so `Pane.paste` still needs a process. One control client answers one request at a time, so concurrent callers serialize behind it, where the process transport runs them at once. An untargeted command sent over control resolves against the attached session, not whichever session a caller meant.

A persistent, general-purpose control-backed transport was investigated and not built: `if-shell`'s guarded branch, and each command inside a semicolon-joined batch, answer as their own separate reply blocks rather than folding into one, so a transport forwarding this library's existing fenced and batched commands to a persistent control client would return truncated or empty results for nearly every typed operation, `Server.snapshot()` included. `docs/decisions/0018-control-backed-transport-rejected.md` has the measurements.

## Following a change

A `ServerMirror` listens through a control client and takes a fresh snapshot for each announcement. 20 windows were created through another client, each timed from sending the command to the mirror publishing a view that held it: the command's own process, tmux's announcement, and the rebuild.

| measure | value |
| --- | --- |
| median, command sent to view published | 18013.8 µs |
| p95 | 37043.4 µs |
| commands the mirror dispatched per change | 2.1 |

A rebuild is a snapshot, two commands. A new window is announced more than once, and announcements that arrive during a rebuild fold into one more, so a change costs one or two rebuilds rather than one per announcement.

## Output through `poll()` and `onReady`

A pane prints 50000 numbered lines; a subscription reads them as the Kotlin `Flow` and fs2 bridges do, polling until empty and then arming a one-shot `onReady`, so no thread waits. The buffer holds the whole flood, so this is the ceiling those bridges sit under.

| measure | value |
| --- | --- |
| wall clock, command to last line | 692 ms |
| lines per second | 72254 |
| frames delivered | 391 |
| events dropped | 0 |

tmux batches output into `%output` frames, so frames are far fewer than lines. The number is tmux's pace as much as this library's: a pane writes to a pty, and tmux reads, parses and re-encodes it before a control client sees it.

## Threads the library holds

Platform threads named `libtmux-*`, counted at each step on a transport bounded at four processes. Virtual threads, such as a mirror's listener, are not counted: they hold no carrier while they wait.

| step | threads |
| --- | --- |
| server open, a session made and listed | 12 |
| after eight concurrent snapshots | 12 |
| a control client attached | 15 |
| an output subscription open | 15 |

Three drain threads per admission slot, and never more however many callers queue: eight concurrent snapshots on four slots held no more than four sequential commands did. A fixed pool starts a new thread for each of its first tasks even while others are idle, so a few commands in a row already hold all of them; each lets go after ten idle seconds, which is how an unclosed transport still lets a program exit. A control client adds three. A subscription adds none.

## What this does not measure

Not measured here: MCP tool call overhead, and the Kotlin and Scala stream layers above `poll()`. Their stress tests account for every event under a producer that outruns the consumer (`FlowBridgeStressTest`, `ObservationStressSuite`); their throughput is bounded by the flood above.
